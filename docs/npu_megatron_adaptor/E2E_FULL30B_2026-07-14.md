# 全 48 层 Qwen3-30B-A3B 单机端到端：bf16 vs mxfp8（2026-07-14）

> 平台：Ascend 950DT ×8（96GB/卡）；CA_verl env = torch 2.8.0 / torch_npu 2.8.0.post4 / **TE-NPU 2.13.0** / **mcore 0.17.2** / megatron_adaptor；CANN 9.1.T551（bundled，T560/b061 亦验证兼容）；模型 Qwen3-30B-A3B 全 48 层 128 专家；gsm8k GRPO。

## 1. 今日工程突破（两道墙俱破）

### (a) 显存墙 —— precision-aware 优化器 offload
`override_optimizer_config.{use_precision_aware_optimizer=True, optimizer_cpu_offload=True, optimizer_offload_fraction=1}`（mcore 0.17 原生，verl 的 `utils/megatron/optimizer.py` 通用透传落地）。
- 片上 HBM 从旧配置的 **69GB 降到 29-32GB**，全 48 层大余量运行、无 OOM。
- 修正：此前归因的 "ParamAndGradBuffer 常驻致 step2 OOM" 实为**未开 precision-aware offload**；开后即解。

### (b) mxfp8 首步 HCCL EI0006 —— 超时
mxfp8 首次前向 lazy init（fp8 量化器 + 首个 EP all-to-all + grouped GEMM 首编译）> 默认 `HCCL_CONNECT_TIMEOUT=120s`，触发 PP p2p `HcclBatchSendRecv` socket 超时（EI0006）。
- 修复：`HCCL_CONNECT_TIMEOUT=HCCL_EXEC_TIMEOUT=900`。bf16 无此首步延迟不受影响。
- 该超时为"等待上限"非稳态延迟，稳态步不触达。

## 2. 结果（干净同布局对比：EP4×TP2×PP2 + precision-aware offload）

### 档 A：small（prompt512 / response256 / mbs1，~10.6k token/步）
| 指标 | bf16 | mxfp8 |
|---|---|---|
| pearson_corr | 0.973 | 0.901 |
| update_actor | 38.3s | 39.3s |
| HBM/卡 | 29.2GB | 31.9GB |

### 档 B：saturated（prompt1024 / response2048 / use_dynamic_bsz，token_len_per_gpu=(P+R)*4=12288，~77k token/步）
| 指标（step2/3 均值） | bf16 | mxfp8 | 比值 |
|---|---|---|---|
| pearson_corr | 0.989 | 0.955 | −0.034 |
| update_actor | 42.7s | 47.9s | **0.89x（mxfp8 慢 ~12%）** |
| gen（rollout，两版都 bf16） | 111.9s | 112.3s | 持平 |
| step | ~190s | ~195s | 持平 |
| HBM/卡 | 29.8GB | 42.6GB | +12.8GB |

## 3. 关键结论

1. **mxfp8 端到端在 RL 尺度不加速，update_actor 反慢 ~12%**（即使 token 打满到 77k/步）。
2. 两个结构性根因：
   - **MoE 每专家 token 未饱和**：128 专家 × top-8，12288 token/gpu/microbatch 摊到每专家仅 ~768（远低于 GroupedLinear 饱和拐点 8192）。MoE FFN 是主算力但其 GEMM 落在 <1x 区。要每专家饱和需 ~131072 token/gpu（RL 尺度不现实、必 OOM）。dense/attention GEMM（M≈12288 > 8192）已饱和会加速，但占比小。
   - **token 非 32 对齐**：dynamic_bsz 打包出的 M 几乎不是 32 倍数 → mxfp8 触发 bf16 回退路径，付量化开销无 fp8 收益。
3. **精度随饱和回升**：mxfp8 corr 0.901（small）→ 0.955（saturated）；bf16 0.973 → 0.989；gap 0.07 → 0.034。
4. **修正历史误判**：此前记录的 "mxfp8 update_actor 1.27x 加速" 是 **PP1（bf16 历史）vs PP2（mxfp8 历史）布局假象**，非 fp8 功劳；同布局对比后加速消失。→ 干净同配置对比是必要的。

## 4. 下一步杠杆
- **32 对齐 token padding**（修 bf16 回退）——最可能把 mxfp8 从 0.89x 拉回 ≥1x，dense/MoE 都受益。
- 加大 `ppo_max_token_len_per_gpu`（*4→*8）——只能让 dense 更饱和，MoE 结构上仍够不到拐点。
- MoE 专家饱和在 RL 尺度结构性受限。

## 5. 复现
- 脚本：`scripts/launch_te30b.sh`（small）、`scripts/run_30b_sat.sh`（saturated）。
- 关键 env：`CANN_ENV=<bundled T551>`、`HCCL_CONNECT_TIMEOUT=HCCL_EXEC_TIMEOUT=900`。
- 布局：EP4×TP2×PP2，param/grad/optimizer offload + precision-aware 优化器 offload，enforce_eager，recompute full。
